## 3. Ответы на вопросы
1. Почему размеры v1 и v2 различаются именно так?
   В чём главная польза многоэтапной сборки в этом проекте?
   Ответ:
      Размер образов зависят от базового слоя образа и файлов, которые потом попадают в финальный образ. При многоэтапной сборке промежуточные инструменты, исходные данные или тесты сборки необязательно попадают в финальный образ.
      Главная польза многоэтапной сборки в этом проекте - это получить более компактный финальный образ, содержащий только необходимые приложения и файлы.
2. Какой тест упал на этапе 3? Почему не появился образ ОБРАЗ:bad?
    Ответ:
      При добавлении записи с длительностью поездки 240 минут должен упасть тест test_minutes_range, так как значение превышает допустимый диапазон.
      Образ velo-alatau:bad не должен создаваться, потому что сборка останавливается на стадии тестирования. Финальная стадия не выполняется успешно, поэтому итоговый образ не формируется.
3. Какие шаги на этапе 4 были CACHED и почему?
   Какие шаги выполняются заново при изменении records.csv?
    Ответ:
      При изменении только app/server.py Docker может использовать кэш предыдущих стадий, поскольку входные файлы для формирования отчёта и тестирования не изменились.
      В частности, должны оставаться в кэше шаги формирования отчёта и тестирования, если их входные данные не изменились. Копирование обновлённого app/server.py в финальную стадию и последующие шаги выполняются заново.
      При изменении records.csv меняется входной файл для формирования отчёта. Поэтому шаги, зависящие от данных, например COPY data/ data/ и RUN python tools/build_report.py, должны выполняться заново. Если отчёт изменился, также могут повторно выполниться копирование тестов и запуск тестов на стадии test, а затем шаги финальной стадии.
